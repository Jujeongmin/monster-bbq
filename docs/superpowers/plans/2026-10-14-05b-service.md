# 05b 장사와 정산 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 밤 장사를 만든다. 가게 단면도에 손님이 들어와 오늘 메뉴를 주문하고, 주문을 누르면 조리 장면으로 확대되어 직접 굽고 끓여 서빙한다. 장사가 끝나면 서버가 검증해 골드·평판을 주고 정산 화면에 보여 준다. 하루 루프(사냥 → 주방 → 장사 → 정산)가 처음부터 끝까지 돈다.

**Architecture:** 손님 배치는 사냥처럼 서버 시드로 정해진다(`shared/service/plan.ts`의 `planService`). 장사 중에는 Phaser 게임 하나에 `ServiceScene`(가게)과 `CookStage`(조리, 장사 모드)를 함께 돌리고, 조리 장면은 숨겨져도 계속 익는다. 확대 전환은 카메라 효과다. 끝나면 서빙 목록(손님, 쓴 재료, 조리 정확도)과 떠난 손님을 `finishService`로 보내고, 서버가 손님·메뉴·재료·시간을 검사해 재료를 차감하고 골드·팁·평판을 계산한다. 결과 요약은 세이브의 `lastService`에 남아 정산 화면이 읽는다(같은 장사 ID 재전송은 아무것도 바꾸지 않음).

**Tech Stack:** TypeScript 5.7, Phaser 3.90, React 18, vitest 3, @agent8/gameserver-node 2.

**Spec:** [조리와 장사 설계](../specs/2026-10-14-cooking-service-design.md) 3·5장, [전체 설계](../specs/2026-10-14-monster-bbq-design.md) 4장 밤 장사·7장 서버 판정 3번.

## Global Constraints

- 계획 02~05a의 제약 전부(서버 판정, `t()`, 레시피 정답 서버 전용 + `check:bundle`, 그림은 승인 후, 코드로 그리지 않음).
- 서버는 조리 과정을 못 본다. 정확도는 클라이언트 보고를 받되 0~1 범위·형식만 검사(고기 등급과 같은 위험 수용).
- **서버 하네스 테스트(`npm run test:server`)는 Windows에서 끝날 때 `isolated-vm` 오류 창을 띄운다. 돌리기 전에 사용자에게 알린다.**
- 손님 이름·성격·대사는 스토리라 정하지 않는다(07에서 후보 승인). 05b의 손님은 이름 없는 숲 주민(종류 번호).
- 도시락은 계획 06.

## Review Focus

- 같은 손님을 두 번 서빙했다고 보고하거나, 아직 오지 않은 손님(도착 시각 전)을 서빙했다고 하면 거부 → Task 3 테스트.
- 주문과 다른 재료 조합, 가진 것보다 많은 재료를 썼다고 하면 거부 → Task 3 테스트.
- 응답이 끊겨 같은 `finishService`를 다시 보내면 골드를 두 번 주지 않음 → Task 3 테스트.
- 메뉴가 비었거나 메뉴의 재료가 하나도 없으면 장사를 시작할 수 없다는 안내 → Task 3 테스트 + Task 7 확인.
- 장사 중 탭을 숨겼다 돌아와도 손님 인내심·조리가 한꺼번에 튀지 않음(dt 50ms 제한) → Task 6 확인.

### Task 1: 장사 규칙 — 손님 배치와 점수

**Produces:**
- `BALANCE.service = { baseCustomers: 4, perReputation: 10, minCustomers: 3, maxCustomers: 10, firstArriveMs: 3000, gapMs: [8000, 14000], patienceMs: [45000, 60000], seats: 4, minMsPerServe: 4000, dishPrice: Record<DishId, number>, premiumBonus: 0.25, tipRate: 0.3, happyAt: 0.75, rep: { happy: 1, left: -2 } }`. 요리 값: grilled_belly 40, garlic_neck 50, belly_ssam 65, honey_rabbit 70, shiitake_grill 18, rib_stew 80, baeksuk 90, chicken_perilla 55.
- `planService(seed, { day, reputation, menu }): Customer[]`, `Customer { id: "c#"; kind: 0|1|2|3; arriveMs; dish: DishId; patienceMs; seat }`. 손님 수 = clamp(base + floor(rep / perReputation), min, max). 도착 간격·인내심·요리·종류는 `seededRandom(seed)`. 자리는 차례로 돌아감.
- `dishScore(accuracy, keys)`: 정확도 × (1 + premiumBonus × 특급 부위 비율). `serveValue(dish, score)`: `{ gold, tip, happy }` — gold = round(값 × (0.6 + 0.4 × min(1, score))), tip = round(값 × tipRate × clamp((score − 0.8) / 0.45, 0, 1)), happy = score ≥ happyAt.

테스트: 같은 시드 같은 손님, 평판이 오르면 손님 수 증가(상한), 요리는 메뉴 안에서만, 도착 시각이 오름차순·간격 범위, ID가 다름 / 특급이 점수를 올림, 정확도 0이면 기본 값의 60%, 팁은 높은 점수에서만, 만족 기준.

- [ ] 테스트 → 실패 확인 → 구현 → 통과 → 커밋 `feat(service): customers from the seed, dish score and value`

### Task 2: 세이브 v4

**Produces:** `SaveData` v4 `{ …v3, version: 4, reputation: number; service: { id; seed; startedAt; menu: DishId[] } | null; lastService: { id; served: number; left: number; sales: number; tips: number; happy: number; repDelta: number } | null }`. v3 → v4(평판 0, 나머지 null), 이전 버전도 차례로. `Verse8Transport` 응답 버전 4.

테스트: 새 세이브, v3 → v4, v1·v2 → v4, 깨진 `service`/`lastService`/`reputation` 정리.

### Task 3: 서버 장사 검증

**Produces:**
- `{ type: "startService" }`: 오늘 메뉴(`save.menu`)가 비면 `no_menu`, 메뉴 어느 요리도 1인분이 안 나오면 `no_ingredients`. 통과하면 `service = { id, seed, startedAt: now, menu }`.
- `{ type: "finishService"; serviceId; served: { customer; keys: string[]; accuracy }[]; left: string[] }`: `serviceId === lastService?.id`면 세이브 그대로(재전송). 검사: 장사 ID 일치, 손님이 계획에 있고 한 번씩, served와 left가 겹치지 않음, keys의 아이템 ID 집합이 그 손님 요리의 레시피(서버 표)와 같고 서로 다름, 키별 사용 합계 ≤ 가진 수, accuracy는 0~1 숫자, `now − startedAt ≥ max(서빙한 손님 도착 시각)`, `≥ 서빙 수 × minMsPerServe`. 통과하면 재료 차감, 골드 += 값+팁 합, 평판 += 만족 손님 × happy + (떠난 손님 + 응대 못 한 손님) × left(0 아래로 안 감), `lastService` 요약, `service = null`. 실패하면 `bad_service`, 세이브 그대로.
- `recipes`가 없으면 `unavailable`.

테스트(vitest): 정상 정산(골드·팁·평판·재료·요약), 재전송 무시, 거부(세이브 그대로): 같은 손님 두 번, 없는 손님, 도착 전 손님, 주문과 다른 재료, 같은 ID 두 등급, 재료 부족, 정확도 1.5·문자열, 다른 장사 ID, 장사 없음, served·left 겹침 / startService: 메뉴 없음, 재료 없음.
서버 하네스: startService 메뉴 없음 거부, finishService 위조 거부(사용자에게 알린 뒤 실행).

- [ ] 테스트 → 실패 확인 → 구현 → 통과 → 커밋 `feat(server): night service opened and settled by the server`

### Task 5: 조리 장면 장사 모드

**Produces:** `CookStage.init({ items, mode: "service", menu: { dish, recipe }[] })`.
- 쟁반: 메뉴 요리의 재료 키만, 개수는 장사 내내 누적(접시마다 초기화하지 않음).
- 위쪽 주문표: 기다리는 손님마다 요리 그림 + 인내심 띠(`game.registry`의 `orders`). 접시를 주문표의 손님에게 끌면, 접시 재료 ID 집합이 그 요리 레시피와 같을 때만 `game.events.emit("service:serve", { customer, keys, accuracy })`, 다르면 "주문과 달라요".
- 오른쪽 도구 칩: 불판·냄비, 칩 테두리에 가장 많이 익은 정도, 타기 직전(닿은 면 > burnAt − 0.15)·넘치기 직전이면 빨갛게 깜빡임, 탭하면 그 도구로.
- "가게로" 버튼: `game.events.emit("service:shop")`.
- 숨겨져도(`setVisible(false)`) 계속 `update`.

확인: 브라우저에서 메뉴 재료만 보이는지, 주문표로 서빙, 다른 요리는 거부, 칩 경고.

- [ ] 작성 → `npx tsc --noEmit` → 브라우저 확인·수정 → 커밋 `feat(service): cook stage in service mode`

### Task 6: 가게 장면

**Produces:** `ServiceScene`(키 `shop`), `ServiceGame.tsx`.
- 손님이 `arriveMs`에 들어와 자리에 앉고, 말풍선에 요리 그림과 인내심 띠. 인내심이 다하면 화내며 떠남(평판 감소 예고 "−2"), 서빙되면 먹고(기쁨) 동전이 튀며 떠남.
- 주문 말풍선을 탭하면 그 요리의 도구로 확대 전환(카메라 확대·페이드 300ms), `service:shop`이면 반대로.
- 일시정지 버튼(둘 다 멈춤). 시계는 `ServiceScene`이 관리하고 dt는 50ms로 자름.
- 모든 손님이 서빙됐거나 떠나면 마감: `service:end { served, left }`.

확인: 손님 입장·주문·인내심·떠남, 확대 전환, 일시정지, 마감.

- [ ] 작성 → `npx tsc --noEmit` → 브라우저 확인·수정 → 커밋 `feat(service): the shop scene`

### Task 7: 하루 흐름 연결과 정산

`DayFlow`: 주방 "장사 준비" → `setMenu` → `startService`(실패하면 이유 안내) → `ServiceGame` → `finishService` → 정산 화면(`Settle.tsx`: 매출, 팁, 손님 수·만족, 평판 변화) → 다음 날. 임시 "재료 모두 팔기" 화면은 없앤다(`sellAll` 행동은 남겨 두되 화면에서 안 씀).

확인(관문): 사냥 → 주방(메뉴) → 장사(서빙 2명 이상, 1명은 놓침) → 정산 숫자가 서버 결과와 같음 → 새로고침해도 골드·평판 유지 → 다음 날.

- [ ] 작성 → `npx tsc --noEmit` + `npx vitest run` + `npm run check:bundle` → 브라우저 관문 → 커밋 `feat(dayflow): the night service and the settle screen`
