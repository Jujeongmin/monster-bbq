# 가게 개편 4단계: 장사 중 메뉴 추가 (설계)

2026-10-20. 가게 개편 순서(2026-10-16 합의) 1 배치 → 2 낮 가게 → 3 설명·효과(구현됨) → **4 장사 중 메뉴 추가** → 5 직원. 사용자가 질문 없이 바로 진행하라고 해서 결정은 대부분 **제 판단**이다. 프로토타입이라 계속 다듬는다.

## 1. 왜

지금은 저녁 주방에서 정한 메뉴와 세트 수가 밤 내내 고정이다. 한 요리가 다 팔리면 손님은 남은 다른 요리로 바꿔 시키고, 모든 그릇이 바닥나면 주문이 자동으로 닫혀 **아직 안 온 손님은 아예 들어오지 않는다**. 냉장고에 재료가 남아 있어도 그 밤에는 쓸 방법이 없다. 데이브 더 다이버 반쵸 스시처럼, 장사 도중 반달이에게 가서 남은 재료로 요리를 더 내게 한다.

## 2. 목표 / 비목표 / 반목표

- **목표**
  - 밤 장사 중 반달이(창구)에서 메뉴판을 열어, 남은 재료로 **이미 낸 요리의 세트를 늘리거나 새 요리를 더한다**.
  - 다 팔려 주문이 닫혔어도, 영업 시간(22시) 전이고 손주가 직접 닫은 게 아니면 추가하는 순간 **다시 손님을 받는다**.
  - 서버가 재료를 확인하고 빼고, 정산이 추가분까지 맞게 검증한다.
- **비목표**: 손님 수·도착 시각·인내심 규칙은 바꾸지 않는다. 요리 빼기·세트 줄이기(이미 뺀 재료 되돌리기)는 하지 않는다. 직원(5단계)은 다루지 않는다.
- **반목표**
  - 손님 계획이 흔들리기: 서버는 연 순간의 메뉴로 손님(시드)을 정한다. 추가한 요리 때문에 손님 명단이 바뀌면 정산 검증이 어긋난다 → 손님 계획은 **처음 메뉴로 고정**.
  - 재료를 두 번 빼기: 응답이 늦어 다시 보내도 한 번만 빠진다.
  - 장사가 멈춘 채 굳기: 서버가 거절하거나 연결이 끊겨도 창을 닫으면 원래 밤이 그대로 이어진다.

## 3. 규칙

1. **여는 곳**: 창구(반달이) 앞에서, 받을 요리가 없을 때 E → "메뉴 추가". 창구 말풍선이 그때 "E 메뉴 추가"로 바뀐다(3단계의 대상 말풍선). 모바일은 행동 버튼. 다 팔렸을 때 처음 한 번 뚜껑이 한 줄: "다 팔렸껑! 재료 남았으면 반달이한테 E, 더 내껑."(문구 승인 대상).
2. **창이 열려 있는 동안 밤은 멈춘다**(시계·손님·인내심). 일시정지와 같다(제 판단: 메뉴를 고르는 동안 손님이 화나서 나가면 억울함).
3. **고를 수 있는 것**: 연구한 요리 중 지금 냉장고 재료로 1세트 이상 되는 것. 오늘 메뉴에 없는 요리는 메뉴 칸 업그레이드(`menuSlots`) 안에서만 더할 수 있다. 줄마다 세트 수 −/+ (재료가 허락하는 만큼), "추가" 한 번에 한 줄.
4. **값**: 새 요리는 저녁 메뉴판과 같은 계산(레벨 가격 × 각성 × 특급 재료 비율). 이미 있는 요리에 세트를 더하면 **그 요리의 오늘 값을 그대로** 쓴다(제 판단: 한 요리에 값이 둘이면 정산과 화면이 복잡해짐. 특급 재료를 더 써도 값은 안 오름 — 창에 "가격 그대로" 표시).
5. **다시 열기**: 다 팔려 닫힌 주문은 추가가 성공하면 다시 열린다. 22시가 지났거나 손주가 "주문 마감"을 눌렀으면 추가는 되지만(남은 손님용) 문은 다시 열리지 않는다.
6. **정산**: 만든 그릇 수(`made`)에 추가분이 들어간다. 그래서 더 내고 못 판 만큼은 지금처럼 "떠난 손님"으로 평판에 반영된다(더 내는 데도 책임이 있음).

## 4. 서버

- 새 행동 `addToMenu { serviceId, dish, sets }`.
  - 조건: 장사 중(`stage === "kitchen"`이고 `service`가 있고 `serviceId`가 그 밤), 연구한 요리, 새 요리면 메뉴 칸 여유, 세트 1 이상이고 그 줄 합계 ≤ `MAX_SETS`, 재료 충분(`planShop`과 같은 계산).
  - 하는 일: 재료를 빼고 `service.dishes`에 그릇을 더한다(있으면 그 줄 `plates` 증가, 없으면 새 줄). `menu`(다음 날 메뉴판 기본값)도 같이 늘린다.
  - **중복 방지**: 클라이언트가 추가마다 새 `addId`를 붙이고, 서버는 그 밤에 받은 `addId`를 `service.adds`에 남긴다. 같은 `addId`가 다시 오면 아무것도 안 바꾸고 지금 세이브를 돌려준다.
- `PendingService`에 `planMenu: DishId[]`(연 순간의 요리 순서)와 `adds: string[]`를 더한다. 손님 계획(`planService`)은 클라이언트·서버 모두 `planMenu`로 만든다. 예전 세이브(없음)는 `dishes`의 요리 순서로 읽는다.
- 정산(`settleService`)의 그릇·값 표는 지금처럼 `service.dishes`(추가분 포함)를 쓰고, 손님 표는 `planMenu`로.

## 5. 화면

- **메뉴 추가 창**: 밤 화면 위에 저녁 주방 메뉴판과 같은 줄 모양(요리 그림·이름·가격·"재료로 N세트"·−/+), 위에 "메뉴 칸 3/4", 아래 "추가"와 "닫기". 재질은 지금 메뉴판 그림을 그대로 쓴다(새 그림 없음, 제 판단).
- 보내는 중에는 버튼을 잠그고 "반달이가 준비하는 중…". 실패하면 창 안에 이유 한 줄(재료 부족·칸 부족·연결 실패)과 다시 시도.
- 성공하면 창이 닫히고, 반달이가 내미는 포즈 + 메뉴 패에 새 요리 아이콘·그릇 수가 통 튀어 나옴, 다시 열렸으면 "다시 손님 받는다!" 띠(3단계 띠와 같은 모양).
- 2D 대체 가게(WebGL 없을 때)도 같은 창을 쓴다. 여는 방법은 그쪽 행동 키 그대로(제 판단, 만드는 사람이 맞춤).

## 6. 밤 상태(클라이언트)

- `Shift`에 `addPlates(dish, plates)`(그릇 더하기, 새 요리면 주문 목록에 추가)와, 다 팔림으로 닫혔는지 구분하는 값(`closedBy: "soldOut" | "player" | "clock"`)을 둔다. 추가 성공 후 `closedBy === "soldOut"`이고 22시 전이면 주문을 다시 연다.
- 새로고침(세션 저장)에서 이어 할 때도 추가분이 남는다(밤 상태의 그릇 수 + 서버 세이브의 `dishes`).

## 7. 정한 것 / 맡기는 것

**정한 것(제 판단)**: 창구 E로 열기, 창이 열리면 밤이 멈춤, 이미 낸 요리는 값 그대로, 손님 계획은 처음 메뉴로 고정, 추가마다 `addId`로 중복 방지, 못 판 추가분은 평판에 반영, 새 그림 없음.

**맡기는 것**: 창의 세부 배치, 메뉴 패에 새 요리가 들어갈 자리(지금 6칸), 2D 쪽 열기 버튼 위치, 예전 세이브 읽기 방식.

## 8. 확인 방법

- 서버 규칙 테스트: 정상 추가(새 요리·기존 요리), 재료 부족·칸 부족·장사 아님·다른 밤 id 거절, 같은 `addId` 두 번이면 한 번만, 추가 뒤 정산이 추가 그릇을 팔 수 있고 손님 명단은 그대로.
- `Shift` 테스트: 다 팔림으로 닫힌 뒤 추가하면 다시 열려 다음 손님이 들어옴, 손주가 닫았거나 22시 뒤면 안 열림.
- `npm run test:server`(서버 행동이 바뀜), 1280×720 headless로 다 팔림 → 창구 E → 추가 → 다시 손님 받기 장면.
